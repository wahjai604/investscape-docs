# InvestScape: A Decision-Grade Strategy Report for a Solo, Bootstrapped Founder

## TL;DR
- **Build the calculation engine yourself first — it is genuinely the right beginner project — but treat correctness, not "working code," as the deliverable, and do NOT let an AI assistant write it for you unsupervised.** A pure, deterministic, UI-less financial engine validated by golden tests and property-based tests is the one component whose learning curve you can actually climb. Everything around it (auth, deployment, payments, DevOps) is where beginners drown — defer or hire that.
- **Demo only genuinely-functional engines to sophisticated real estate pros and investors; label every non-live element "for illustrative purposes only — sample data."** Real estate professionals will test your numbers against their spreadsheets within minutes, and misrepresenting functionality to investors is a securities-law risk in BC, not just a reputational one.
- **Engage the meetup database person as a paid contractor on a milestone trial for 3–6 months before any equity — and get a written IP-assignment plus a check on his day-job employment contract first.** A "database professional" fills perhaps a third of what InvestScape needs; equity granted now, without vesting and IP assignment, is the single most dangerous irreversible mistake available to you.

## Key Findings

1. **AI-generated prototype HTML cannot be "sequenced" into professional code by a single conversion step — but restructuring it into clean, semantic, tokenized code is far more valuable if your destination is coded front-end than if it is WeWeb.** WeWeb cannot import an HTML codebase at all; you rebuild the UI regardless. Your prototype's real portable asset is a JSON design-token file, not its markup.

2. **The evidence on AI coding assistants for beginners is genuinely alarming and directly relevant to your "willing to learn to code" plan.** Multiple 2025–2026 controlled studies show AI produces an *illusion of competence*: novices produce working code but fail to learn, and even experienced developers were measurably *slower* with AI while believing they were faster.

3. **A financial calculation engine is hard in ways that have nothing to do with general programming** — floating-point money errors, banker's rounding drift over 300 amortization periods, root-finding convergence failures in IRR, and day-count/compounding conventions. These are exactly the failures that will be invisible until a customer catches them.

4. **1,000 paying customers is ambitious but not impossible for this niche** — CREA reports more than 160,000 realtors in Canada alone, plus a large investor and mortgage-broker population, and comparable tools like DealCheck charge $10–$29/month. But pre-selling a product not yet built triggers real BC consumer-protection refund obligations.

5. **The co-founder situation carries the highest irreversible risk in the whole plan.** Canadian law gives you weaker automatic IP protection than US founders assume, has no 83(b) election, and a moonlighting developer's day-job employer may own the code he writes for you.

## Details

### STRAND 1 — Converting AI-generated prototype HTML into professional, portable front-end code

**Your core question, answered directly:** No, Claude cannot reliably take vibe-coded mockups and "just sequence the code the way a human would build an HTML5 site" in one clean pass that a back-end developer will happily inherit. It can *substantially improve* the code, but AI-generated front-end code has well-documented, systematic structural problems, and the improvement is an iterative, supervised refactor — not a one-click conversion.

**What the evidence says about AI-generated front-end code quality.** This is now well-documented rather than anecdotal. Google's DORA 2025 report found that roughly 90% of surveyed developers use AI at work and that "AI adoption does continue to have a negative relationship with software delivery stability" — i.e., more AI, less stable delivery. Independent engineering telemetry points the same way with sharper numbers: Faros AI's analysis of ~22,000 developers reported pull-request size up ~51%, time in PR review up sharply, and bugs per developer up ~54% in AI-heavy workflows (these specific percentages are from Faros, not DORA; treat the exact figures as vendor telemetry rather than peer-reviewed). A GitClear analysis of 153 million code changes documented rising code duplication and "churn." A Carnegie Mellon difference-in-differences study of Cursor's impact, tracking projects into mid-2025, found AI "briefly accelerates code generation, but the underlying code quality trends continue to move in the wrong direction." The recurring specific defects that a developer inheriting AI HTML will complain about: giant single files (one reported page component was 2,800 lines), inconsistent naming (camelCase/snake_case/kebab-case mixed in one codebase), duplicated helper functions written five different ways, files dumped wherever with no logical grouping, and — critically for you — a bias toward "local functional correctness over global architectural coherence." An arXiv literature review confirmed AI code "often appears syntactically valid" but contains "logical flaws, insecure patterns, or deviations from best practices," and is "less readable due to overly concise structures, unconventional variable naming, or lack of meaningful comments."

**What a professional front-end handoff actually needs.** The current standards a developer expects: semantic HTML5 (real `<header>`/`<nav>`/`<main>`/`<section>` structure, not `<div>` soup); separation of concerns (no inline styles, CSS in its own layer); a CSS methodology (BEM, utility-first/Tailwind, or CSS Modules) applied consistently; CSS custom properties (variables) for design values instead of magic numbers scattered through the file; ES-module JavaScript organized into logical files; and a predictable folder structure with comments explaining intent. Accessibility (WCAG) — proper labels, roles, contrast, keyboard navigation — must be baked in during restructuring, because retrofitting it into AI-generated `<div>` soup is far more expensive than building it in.

**The single most valuable portable artifact: a JSON design-token file.** This is the real answer to "how do I make this portable across front-end targets." The W3C Design Tokens Community Group (DTCG) format reached its first stable version (2025.10) in October 2025. It is a vendor-neutral JSON file (`.tokens.json`) where each token has `$value`, `$type`, and `$description`, supporting aliasing (`{color.brand.500}`) and consumed by Style Dictionary (v4 has first-class DTCG support), Tokens Studio, Figma, Tailwind, and native platforms. Extract your colors, spacing scale, typography, and border-radii from the Claude prototypes into a single DTCG JSON file. That file survives *any* rebuild — WeWeb, React, or plain HTML — and is the one thing a developer can consume verbatim. This is worth doing regardless of which route you choose.

**What WeWeb can and cannot ingest — from WeWeb's own docs.** WeWeb's FAQ is explicit: "You cannot import a full codebase or site directly into WeWeb. WeWeb isn't an HTML/CSS parser; instead, you rebuild your frontend within WeWeb's editor... an import tool or one-click migration from other services is not available at this time." What WeWeb *can* consume: custom coded Vue components (with a `ww-config.js` metadata file defining editable properties), custom JavaScript (via `thisInstance` and lifecycle hooks like `onMounted`), external libraries (e.g., Highcharts) inside custom components, and page/project-level custom code snippets. WeWeb docs advise keeping component content "as flat as possible" and warn to "avoid... defining styles like padding which are handled by the Editor." So the optimally-prepared source for WeWeb is: your design tokens as a JSON/CSS-variable system, plus any genuinely complex widgets (your charts, your amortization table) packaged as self-contained custom Vue components — not a pile of HTML pages. *(These are vendor-stated capabilities from WeWeb's own documentation.)*

**The strategic implication:** "restructure the HTML properly" is worth much more if your destination is coded front-end (React/Next/Vue/plain HTML+JS), where clean semantic HTML and a token system are directly reusable. If the destination is WeWeb, you rebuild the layout by hand no matter how clean the HTML is, so the payoff of a full HTML refactor is lower — the tokens and the custom components are what carry over. This is an argument in favor of a coded thin front-end over WeWeb for your Route 2, given you already have Claude-generated HTML as the design source of truth.

### STRAND 2 — Can *this specific person* realistically learn to build the financial calculation API himself?

**The honest verdict: Yes for the pure calculation library; no (not yet, not alone) for the full production API around it.** These are two very different projects, and conflating them is the trap.

**Why a financial engine is hard in ways general programming is not:**

- **Floating-point money.** `0.1 + 0.2 = 0.30000000000000004` in JavaScript because IEEE 754 binary floats cannot represent decimal fractions exactly. Over a 300-period amortization schedule these errors accumulate. Standard mitigations: store money as integer cents, and/or use an arbitrary-precision decimal library. The practical 2026 landscape: **decimal.js** and **big.js** (small, arbitrary-precision decimal arithmetic — big.js is the most commonly recommended for money), **bignumber.js**, and **Dinero.js**/currency.js for money-specific formatting. The **TC39 Decimal proposal** would add native decimals to JavaScript but is still a proposal, not shipping — you cannot rely on it. Verdict: use big.js or decimal.js, and represent money as integer minor units where you can.

- **Banker's rounding.** Round-half-even (banker's rounding) is numerically unbiased and required by some regulations; round-half-up is the everyday convention. Getting this wrong causes cent-level drift that compounds across an amortization schedule and makes your output disagree with a bank's statement — the exact thing a mortgage broker will notice instantly. You must implement *both* and know which applies where.

- **Root-finding for IRR/XIRR/MIRR.** IRR has no closed-form solution; you solve it numerically. Newton-Raphson converges fast (quadratic) but "may fail to converge or converge to a wrong root if the initial guess is not close to a root, or if the derivative is close to zero." Real production XIRR libraries hit exactly this: multiple documented GitHub issues show "Newton-Raphson failed to converge" on real cashflow data that Excel solves fine. The robust pattern used by mature libraries (PhpSpreadsheet, Python's xirr) is: try Newton-Raphson, and **fall back to bisection or Brent's method** (which always converge when the root is bracketed) on failure. IRR can also have multiple real roots when cashflows change sign more than once — you must handle that, not just return the first answer.

- **Day-count and compounding conventions.** Actual/365, actual/360, and 30/360 give different interest for the same period; date arithmetic has leap-year, month-end, and timezone pitfalls.

- **Canadian vs US compounding — with the exact formula you need.** By the Interest Act, Canadian fixed-rate mortgages compound semi-annually, not monthly. The correct effective monthly rate is **`(1 + annual_rate/2)^(1/6) − 1`**, NOT `annual_rate/12`. For a 5% mortgage that is 0.41239%/month (Canada) versus 0.41667%/month (US monthly compounding) — a real difference that compounds over 300 payments and saves a Canadian borrower roughly $4,600 on a $500,000 mortgage at 5% over 25 years. If you use a US formula on a Canadian mortgage your payment is visibly wrong. This is validatable against authoritative Canadian mortgage calculators. **CMHC insurance premiums** (which you must compute) are set by CMHC as a percentage of the loan by loan-to-value band: **4.00% for 5–9.99% down (90.01–95% LTV), 3.10% for 10–14.99% down (85.01–90% LTV), 2.80% for 15–19.99% down (80.01–85% LTV)**, with a 0.20% surcharge for amortizations beyond 25 years (confirmed against CMHC's own premium table and corroborated by Ratehub). The **stress test** qualifying rate is the greater of 5.25% or contract rate + 2%.

**Testing is the actual product, and this is learnable.** How real fintech teams establish confidence: (1) **unit tests** hard-coding known inputs and expected outputs to the exact cent; (2) **golden tests** comparing full output (e.g., an entire amortization schedule) against a known-good reference file — useful as a confidence check that changes "look right"; (3) **property-based testing** with **fast-check**, which generates hundreds of randomized inputs and checks invariants (e.g., "total repayment ≥ principal," "sum of principal portions equals original balance," "remaining balance hits exactly zero at term"), then automatically shrinks any failing case to a minimal counterexample. Fintech practitioners describe exactly this stack (Jest + Decimal.js for exact-cent unit tests, fast-check for properties). This is the discipline that separates "the math looks right" from "the math is right." A motivated non-professional can absolutely learn to write these tests; doing so is the single highest-leverage skill in the whole project.

**The realistic full scope beyond the math** — and what a beginner can defer: **Cannot defer:** input validation (use Zod schemas), correct error handling, and the test suite above. **Can defer / keep minimal at first:** authentication, rate limiting, API versioning, sophisticated logging/observability, CI/CD, secrets management, monitoring. The 2026 tooling that lowers the barrier: **TypeScript over plain JavaScript** (the type system catches whole classes of errors before runtime and is worth the extra learning for a money engine); lightweight frameworks (**Hono**, Express, or Fastify); and simple hosting (Cloudflare Workers or a basic Node host). A calculation API with no database and no user state is about the smallest deployable surface possible.

**The critical evidence on whether AI actually helps you *learn*.** This is the part you must internalize before deciding. The **METR randomized controlled trial** (arXiv 2507.09089, July 2025): 16 experienced open-source developers, 246 real tasks. They *forecast* AI would make them 24% faster; they were actually **19% slower** with AI; and *afterward they still believed they'd been 20% faster.* The gap between perceived and measured productivity was a complete disconnect — for experts, on code they knew well. For *novices* the picture is worse. A 2026 randomized study on skill formation found AI use "impairs conceptual understanding, code reading, and debugging abilities, without delivering significant efficiency gains on average," and that "participants who fully delegated coding tasks showed some productivity improvements, but at the cost of learning the library." Multiple education studies document an "illusion of competence": students rate their understanding as high during AI-assisted work, then fail when the AI is removed — one student's words: "You think you understood how the code worked, but trying to create it on your own shows you didn't fully get it." Anthropic's own research concludes "cognitive effort—and even getting painfully stuck—is likely important for fostering mastery." **The direct implication for you:** if you let Claude write the engine and you approve output that looks right, you will produce something that *appears* to work, you will believe you understand it, and you will be wrong on both counts in a way you cannot detect — which for a financial engine is the worst possible outcome. Use AI in explanatory/learning mode, type the code yourself, and prove correctness with tests you designed.

**Is the "pure calculation engine is the best possible first project" argument sound?** Largely yes. The reasoning holds: deterministic pure functions, no UI, no auth, no persistent state, no concurrency, input-in/number-out, therefore exhaustively testable. That genuinely is the ideal shape for a first serious coding project, and it isolates the one part you cannot safely outsource your understanding of. What it leaves out: (1) the numerical-methods subtlety (root-finding robustness) is deceptively deep and not "beginner" in the algorithmic sense; (2) "exhaustively testable" is only true if you can *specify the correct answers*, which requires you to already understand the finance cold — fortunately, as a licensed realtor and developer, you do, and that domain expertise is your single biggest advantage here; (3) it still needs the boring correctness scaffolding (decimal handling, rounding policy) that is easy to underestimate.

**Realistic timeline (estimate, labelled as such).** For someone with your profile — old HTML, some JS, strong IT/networking fundamentals, motivated, part-time — a defensible estimate: **Learning phase: 2–4 months** part-time to reach working fluency in TypeScript, testing (Jest + fast-check), and decimal/money handling. **Building phase: 4–8 months** part-time to build, test, and validate the full engine (amortization both conventions, cash-flow projection, IRR/XIRR/MIRR with robust solvers, DSCR, GDS/TDS, CMHC, capital stack, portfolio rollup) against golden references. Call it **roughly 6–12 months part-time to a correct, tested, deployed calculation API.** This is an estimate, not a guarantee; the variance is enormous and depends almost entirely on whether you build the testing discipline early or skip it.

### STRAND 3 — Demo-driven validation, focus groups, and pre-selling

**Run moderated usability tests, not focus groups.** The usability-research literature (Nielsen Norman Group) is clear that focus groups (moderated group conversations of 5–10 people about attitudes) are weak for evaluating whether a *tool works*, because group dynamics produce false-positive enthusiasm and opinions rather than observed behavior. What you want is **moderated one-on-one usability testing**: watch a real estate professional try to analyze a real deal with your tool, in silence, and see where they get stuck. NN/g's foundational finding, from Jakob Nielsen's "Why You Only Need to Test with 5 Users" (2000), built on Nielsen & Landauer's 1993 model: **~5 users per round uncovers ~85% of usability problems**, and testing more users yields rapidly diminishing new insights (~15 users approaches ~100%) — so run *small, iterative* rounds rather than one big study. Use 15–20+ participants only if you need quantitative benchmarks. To avoid false positives: give them a real task with their own numbers, don't ask "would you pay for this?" (everyone says yes to be nice), ask "what do you use today and what did it cost you last time it failed?"

**Pre-selling: real, but legally and reputationally loaded in BC.** Established playbook: founding-member/lifetime deals at 20–40% off eventual price, tiered early-bird pricing, a clear delivery timeline ("access Q_ 2026"), an explicit refund policy, and a communication commitment. Letters of intent are safer than pre-payment but weaker signal; actual pre-payment is the real validation. **The BC-specific risk you must respect:** under the Business Practices and Consumer Protection Act, a contract for goods/services the customer doesn't get right away is a "future performance contract," and Consumer Protection BC states that if a customer exercises cancellation rights "they may be entitled to a full refund within 15 days," and the supplier must refund "all money received in respect of the contract" within 15 days of a valid cancellation. Practically: if you take pre-payments and slip your delivery date, customers can cancel and you must refund fast — so treat pre-sale money as a refundable liability, not revenue you can spend. *(General information — confirm with a BC lawyer before taking pre-payments.)*

**What investors want vs. red flags — and the securities-law line you must not cross.** At pre-revenue, investors want evidence of demand (a working core, real user reactions, a waitlist or pre-sales) and a credible team — not a fully-built product. The bright line is honesty about what is real. **Misrepresenting product functionality to investors is a securities-law violation in BC, not merely bad manners.** The BC Securities Act s.50 prohibits making a statement you know or reasonably should know is a misrepresentation, and s.50(3) prohibits, in promotional activity, statements or omissions "that a reasonable investor would consider important" — a standard the BCSC and securities lawyers note is *broader* than a strict "material fact" test (it does not even require the statement to concern a material fact). Directors and officers carry personal liability, mitigated by a due-diligence defence. The cautionary archetype is Theranos: the SEC charged that Holmes and Balwani "made numerous false and misleading statements in investor presentations, product demonstrations, and media articles"; Holmes was sentenced to 135 months (11 years, 3 months) in prison, and Theranos staged demos where, per John Carreyrou's reporting, "a fake result was sent over from California... recorded... displayed during a demo to investors." As one securities lawyer put it: "It's one thing to project optimism and confidence; it's quite another to lie and defraud." **The accepted convention for demoing non-functional elements** is explicit labelling — "for illustrative purposes only," "sample data — not a live calculation," "for demonstration purposes only," "hypothetical and illustrative purposes only" — language drawn directly from standard financial-disclaimer and contract practice. Use it visibly on every screen that isn't computing live.

**Market sizing: is 1,000 paying customers realistic?** The addressable market is large. CREA states its membership "includes more than 160,000 real estate brokers, agents and salespeople working through 63 real estate boards" (industry compilations cite ~158,000–165,000), and IBISWorld counts ~103,500 real estate sales & brokerage businesses in Canada (2026), plus a substantial population of active residential real estate investors (Statistics Canada's Canadian Housing Statistics Program tracks these) and mortgage brokers — and the US market is roughly 10× larger. Comparable prosumer tools show the price points: **DealCheck** (founded 2015, San Diego) runs a free-forever Starter tier, Plus at $10/month billed annually ($14 month-to-month), and Pro at $20/month billed annually ($29 month-to-month), and describes itself as used by "several real estate investors, agents, wholesalers, and other professionals." Others in the space: Mashvisor, Rentometer, Stessa, Landlord Studio, RealData, DealMachine. **Benchmarks (estimates):** prosumer real estate SaaS ARPU commonly sits in the ~$10–$50/month range; at, say, $30/month, 1,000 customers is $360k ARR. Against a Canadian base of 160,000+ realtors plus investors, 1,000 paying customers is well under 1% penetration — **ambitious for a solo bootstrapper on distribution grounds, but not implausible on market-size grounds.** The binding constraint will be customer acquisition (CAC) and churn, not total addressable market. Your instinct that "1,000 sounds impossible" but pre-payment is achievable is directionally right: getting the first 20–50 paying believers is a different, easier problem than scaling to 1,000, and you should size your validation around the first 50.

**Demo sequencing for credibility with sophisticated users.** Real estate professionals will immediately test your numbers against their own spreadsheets. Therefore make **genuinely functional first, in this order:** (1) mortgage payment + amortization (both Canadian and US) — the most-checked number and the one that instantly destroys credibility if wrong; (2) cash-flow projection and DSCR; (3) IRR/equity multiple; (4) GDS/TDS + stress test + CMHC. Leave portfolio rollup, the AI narrative layer, and internationalization as clearly-labelled illustrative mockups until the core is trusted. Credibility is won or lost on the amortization schedule.

### STRAND 4 — The prospective technical co-founder (Canada/BC specifics)

*(General legal/tax information — you must confirm all of this with a BC startup lawyer and a CPA before acting. Canadian rules differ materially from the US norms most startup content describes.)*

**Skills-gap reality check — this is the most important finding in the strand.** A "database professional" (DBA/data engineer/database developer) overlaps with only a fraction of what InvestScape actually requires. The project needs full-stack development, API engineering, authentication and row-level security (RLS), DevOps/deployment, front-end integration, payment integration (Stripe), monitoring, and incident response. A database specialist genuinely adds value on schema design, RLS policies, query performance, and data integrity — real strengths for a portfolio-analytics product. But he would *not* automatically cover the calculation engine, the front-end, payments, or ongoing ops. "Can deploy on Supabase" is a much smaller claim than "can build and operate this product." Do not assume database expertise equals the technical co-founder you need; scope his contribution to what he can actually own.

**Trial before equity — the single most important structural recommendation.** He is someone you met recently at a meetup and who would be moonlighting. Both facts scream *trial first.* The credible path: engage him as a **paid contractor on defined, milestone-based deliverables for 3–6 months** (e.g., "design and deploy the Supabase schema with RLS for portfolio data; deliver X by date Y"). Evaluate: does he ship on time while holding a day job? Is his work clean? Does he communicate? Only after a successful trial do you discuss equity. This converts an irreversible decision (equity) into a reversible one (a contract).

**Equity, if it gets there.** A late-joining, part-time technical contributor to a company that already has an idea, domain expertise, existing IP, and an incorporated entity is *not* an equal 50/50 partner. Frameworks: standard fixed splits with vesting, or the **Slicing Pie / dynamic equity model** (Mike Moyer), which allocates equity from logged contributions (time at below-market rate, cash, expenses) and is well-suited to exactly your situation where commitment levels are unequal and unproven. Guidance for someone joining a "going concern" (not day-zero) suggests meaningfully less than original-founder equity and a shorter cliff. Given part-time/moonlighting status and a late start, a modest minority stake — heavily vested, milestone-gated — is appropriate.

**Vesting is non-negotiable.** Standard: **4-year vesting with a 1-year cliff** (nothing vests before month 12, then monthly/quarterly). Without it, a co-founder who leaves after 8 months keeps a large stake in a company you then build for years — the classic "dead equity" cap-table poison that blocks future hiring and fundraising. Consider single-trigger (termination) vs double-trigger (acquisition + termination) acceleration, negotiated carefully. Because he's part-time and unproven, consider milestone-based vesting on top of time-based.

**IP assignment — a specific Canadian trap.** Get a **written IP-assignment agreement (a PIIA) signed before he contributes a single line of code.** Under Canadian law, absent a written agreement, the default is *not* founder-friendly: for patents, "the general rule in Canada is that an employee will own his or her own invention unless there is a contractual duty to transfer" it; for copyright, ownership "does not automatically pass to an employer unless the employee was hired, expected or directed to develop that kind of work." So without a signed assignment, *he* may own the code he writes for InvestScape. **The moonlighting problem compounds this:** his day-job employment contract may contain an invention-assignment/IP clause that assigns his inventions to *his employer* — potentially including code written after hours for your venture. Canadian courts (e.g., the Comstock case and the Ontario Court of Appeal's Nexus Solutions line) look at whether the work fell within the scope of employment, but the safe assumption is danger. **Before he contributes anything, review his employment agreement for IP and moonlighting clauses**, and if there's any doubt get him a written waiver/acknowledgement from his employer. This is a genuine "his employer could later claim your core IP" risk.

**Canadian corporate and tax mechanics (differ sharply from US norms):**
- Issuing shares from your existing BC company to a new co-founder is straightforward mechanically (board/shareholder resolutions, subscription agreement) but do it *inside* a **shareholders' agreement** with essential clauses: vesting, drag-along/tag-along, right of first refusal, shotgun/buy-sell, non-compete/non-solicit, dispute resolution, deadlock-breaking, and share-buyback-on-departure provisions.
- **Shares vs options:** shares give ownership now (with vesting/reverse-vesting); options give a right to buy later. For an unproven part-timer, options or heavily-reverse-vested shares reduce your risk.
- **Canada has NO equivalent to the US 83(b) election.** US startup advice about "file your 83(b) within 30 days" simply does not apply. Instead, under the Income Tax Act, stock received for services can trigger a subsection 7(1) employment benefit. **The practical consequence:** issue shares to founders at **nominal/near-zero value at the earliest (incorporation) stage**, when the company is worth almost nothing, so there is little or no taxable benefit. Issuing shares *later*, once the company has demonstrable value, can create a taxable benefit for the recipient. This is a strong reason to settle the cap table *before* the product has value — but that collides with "trial first." The resolution: keep the company low-value on paper, use options or a subscription at fair value, and take CPA advice on timing.
- **Lifetime Capital Gains Exemption (LCGE):** for 2026, QSBC shares qualify for an LCGE of **$1,275,000** (indexed ~2.0% up from the $1,250,000 base introduced in Budget 2024; the earlier proposed capital-gains inclusion-rate increase was cancelled in Budget 2025 and never passed into law, so the 50% inclusion rate remains). To qualify, the shares must meet the QSBC tests (broadly, a Canadian-Controlled Private Corporation where ≥90% of assets are used in an active business at sale, and a 24-month holding/asset test). This is a meaningful future tax benefit for both of you — another reason to get the structure right early with a CPA.

**Structuring the moonlighting arrangement so it can work:** define minimum weekly hours in writing, tie equity to milestones, set an explicit trigger and timeline for going full-time (e.g., "converts to full-time when the company can pay $X salary or raises $Y"), and hold quarterly contribution reviews. **If the partnership fails:** the shareholders' agreement must contain a share-buyback right at a pre-agreed valuation formula (or independent valuation), so you can cleanly remove a departed part-timer and avoid a frozen cap table.

### STRAND 5 — Synthesis: the Route 1 → Route 2 decision

**Should he build the calculation API himself, hire it out, or split it?** **Split it, learning-first.** Build ONE engine yourself end-to-end — the mortgage/amortization engine (both Canadian and US), fully tested with golden and property-based tests, deployed as a tiny API. This is your learning project and your credibility anchor. Then honestly assess at that checkpoint: if you have a correct, tested, deployed engine and you understand every line, continue building the remaining engines yourself. If after ~3 months you're producing code you can't prove correct and can't debug, concede — hire a contractor for the remaining engines and keep ownership of the test specifications (which encode your domain expertise). Your prior research conclusion — a standalone, well-tested calculation API with a thin front-end client — is correct and this report reinforces it.

**Should the demo include all engines as vibe-coded illustrations, or only functional ones?** **Functional core, labelled illustrations for the rest.** Make mortgage/amortization, cash flow, DSCR, and IRR genuinely functional before demoing to any sophisticated user or investor. Everything not yet live gets a visible "sample data — for illustrative purposes only" label. This is both a credibility strategy (pros test the math) and a legal necessity (BC securities-law misrepresentation risk with investors).

**How should the co-founder be engaged?** **Paid milestone contractor for 3–6 months → then equity, if earned.** No equity, no share issuance, and no code contribution until (a) a signed IP-assignment/PIIA is in place, (b) his day-job employment contract has been checked for IP/moonlighting clauses, and (c) he has delivered on a defined trial. Then: a modest, heavily-vested (4-year/1-year-cliff, milestone-gated) minority stake inside a full shareholders' agreement with buyback provisions. Consult a BC lawyer and CPA on the share-issuance timing given no-83(b) and subsection 7(1).

**The strongest argument against my own recommendation:** that time spent learning to code is time not spent selling, and for a solo bootstrapper *distribution*, not code, is usually the thing that kills the company. A purist would say: don't learn to code at all — pre-sell first, and if you can't get 20 people to pay, no engine matters; if you can, use that money to hire the engine immediately and spend 100% of your time on customers. This is a serious argument. My recommendation partially concedes to it: the "build one engine, then decide" checkpoint exists precisely so you don't sink 12 months into coding before validating demand. But I still favor learning the *one* engine yourself, for two reasons specific to you: your domain expertise means you're the best-positioned person alive to specify and validate this math, and a founder who understands his product's core engine negotiates from strength with every future developer hire. If you had no finance background, I'd tell you to skip coding entirely.

## Recommendations

**Stage 0 (now → 1 month) — De-risk the irreversibles and validate demand cheaply.**
- Do NOT issue any equity or let the meetup developer write code yet.
- Extract a DTCG JSON design-token file from your Claude prototypes — this is portable across every future route.
- Build a clickable demo of the mortgage/amortization screen with clearly-labelled "sample data — for illustrative purposes only" on anything not computing live.
- Run 5 moderated one-on-one usability sessions with real realtors/investors using their own deal numbers. Do not ask "would you buy"; watch what breaks.
- *Benchmark that changes course:* if you cannot get 5 target users to engage seriously, the problem is positioning/market, not code — fix that before building anything.

**Stage 1 (months 1–4) — Learn by building ONE real engine.**
- Learn TypeScript + Jest + fast-check. Use AI only in explanatory mode; type all code yourself.
- Build and deploy the mortgage/amortization engine (Canadian `(1+r/2)^(1/6)−1` and US monthly), validated with golden tests against authoritative Canadian calculators and property-based invariants.
- In parallel, open pre-sales: founding-member lifetime deal at 20–40% off, explicit delivery date, explicit refund policy, pre-sale money ring-fenced as a refundable liability (BC BPCPA). Target the first 20–50 paying believers.
- *Checkpoint / course-change triggers:* If you have a correct, tested, deployed engine you understand → continue to Stage 2 building the rest yourself. If you're producing code you can't prove correct after ~3 months → concede and hire a contractor for the remaining engines (keep owning the test specs). If pre-sales convert (say, 20+ pre-payments) → strong signal to invest further; if near-zero after real outreach → stop and re-examine the product.

**Stage 2 (months 4–10) — Complete the engine suite and trial the developer.**
- Build remaining engines (cash flow, IRR/XIRR/MIRR with Newton-Raphson + bisection/Brent fallback, DSCR, GDS/TDS + stress test, CMHC premiums, capital stack, portfolio rollup), each golden-tested.
- Engage the developer as a paid milestone contractor on the database/Supabase layer — only after a signed PIIA and an employment-contract IP check. Evaluate delivery, quality, communication, reliability under moonlighting constraints.
- Engage a BC startup lawyer (shareholders' agreement, IP, share-issuance timing) and a CPA (subsection 7(1), QSBC/LCGE structuring). Budget: legal formation docs commonly run a few thousand dollars.

**Stage 3 (months 10+) — MVP, equity decision, and scale.**
- Ship the Route 1 MVP (thin coded front-end + your tested calculation API) to paying customers.
- If the developer's trial succeeded and you're converting customers, negotiate a modest, heavily-vested, milestone-gated minority equity stake inside a full shareholders' agreement with buyback provisions.
- Use revenue to hire the Route 2 production team. *Benchmark to trigger hiring:* recurring revenue that covers a contractor's cost and a churn rate low enough that acquisition compounds.

**Cost posture throughout:** near-zero cash in Stage 0–1 (your time + hosting + a Claude subscription); a few thousand dollars for legal/CPA in Stage 2; contractor costs only if the "concede" trigger fires or after the developer trial. This fits a self-funded bootstrap.

## Caveats
- **Legal and tax content is general information, not advice.** BC securities law, the BPCPA future-performance rules, Canadian IP-ownership defaults, the absence of an 83(b) equivalent, subsection 7(1), and QSBC/LCGE all have fact-specific nuances and change over time. Confirm everything with a qualified BC startup lawyer and CPA before issuing shares, signing the developer, or taking pre-payments.
- **The LCGE figure ($1,275,000 for 2026) and the cancellation of the proposed capital-gains inclusion-rate increase are recent and should be reconfirmed against CRA at the time you act.** CMHC premium bands and the stress-test rate are current as of 2025–2026 but are periodically revised.
- **The AI-productivity evidence is genuine but evolving.** The METR RCT studied experienced developers with early-2025 tools and explicitly labels its result historical; METR's follow-up experiment was inconclusive due to selection bias. The novice-learning studies are consistent but the field is young. The direction of the evidence — AI creates an illusion of competence in novices — is well-supported; precise magnitudes are not settled. The Faros AI "51% larger PRs / 54% more bugs" figures are vendor telemetry, distinct from the peer-adjacent DORA findings; treat exact percentages with caution.
- **Vendor and startup-advice sources are commercially motivated.** WeWeb's capabilities are from its own docs (treat feature claims as vendor-stated); equity-split, pre-sales, and no-code comparison content is heavily affiliate-driven — I've leaned on primary/authoritative sources (NN/g, arXiv, DORA, statute, regulators, CMHC, CREA, StatCan) where the stakes are high and flagged the rest.
- **Market-size figures are directional.** Realtor counts (160,000+) come from CREA's own membership statement and industry compilations, not a single regulator-run national rollup; competitor customer counts are not publicly disclosed, so ARPU/conversion/churn/CAC figures are industry estimates, not InvestScape-specific projections.
- **The single biggest risk this report cannot resolve for you** is whether *you specifically* will build the testing discipline rather than shipping code that merely looks right. The entire "build it yourself" recommendation is conditional on that discipline. The Stage-1 checkpoint exists to catch it early if you don't.
