## 1. Container width — page content is indented relative to the ribbon bar ✅ ROOT CAUSE FOUND, fix approved
**Corrected finding (per your follow-up):** This isn't a Library-vs-other-tabs card-density issue — it's a **structural misalignment**. `.ribbon-top` (logo, tabs, search, +New, theme toggle, profile — line 38) spans the **full browser width** with only `padding:9px 24px`, no `max-width`. But the page content underneath it (`My Portfolio` header, KPI cards, everything) renders inside `.wrap{max-width:1680px;margin:0 auto;padding:0 28px}` (line 29), which **centers itself** once the viewport is wider than ~1736px. On a wide monitor this makes the header/KPI content visibly indented from the logo's left edge and short of the profile chip's right edge — exactly what you're seeing. (Note: UNIFIED's own `.wrap` is actually *narrower*, 1240px — the bug isn't "remastered's wrap is too narrow," it's that remastered has *two different width rules* for the ribbon vs. the content below it.)
**Fix (approved — proceed):** Make `.wrap` (or a content-specific container) span the same edge-to-edge width as `.ribbon-top`/`.ribbon-bottom` instead of centering with a fixed max-width — same left/right padding as the ribbon bar so the header, KPI cards, and everything below line up flush with the logo on the left and the profile chip on the right, on any viewport width. Where this frees up horizontal space, add KPI cards along the top/bottom of the Portfolio table rather than leaving dead whitespace (per your instruction — will look at what's currently missing that could fill the row once the width fix is in).

## 10. Currency Risk Exposure — empty/broken render ✅ ROOT CAUSE FOUND AND FIXED 2026-08-16
**Real root cause (not the race-condition guess originally logged here):** `paintPortfolioCharts()` (runs on the **Overview** sub-tab) never called `mountChart('chart-currency-risk', ...)` at all — only `paintRollupChart()` (runs on the **Rollup** sub-tab) did. But `portfolioGeoAndFxHtml()` renders the Currency Risk Exposure *card* — including its `<div id="chart-currency-risk">` placeholder and the separately-computed "Exposure concentration" text row — on **both** sub-tabs. Result: on Overview, the card's text populated correctly (which is why you saw real numbers like "100% USD" and a risk score, not an empty card) but the gauge itself was never painted into that div — permanently blank, on any theme, every time, not a timing/reload race at all.
**On the "100% USD, skew 100" text you saw:** that part is expected, not a bug — with only two currencies in this model (home currency vs. one foreign currency), a Canadian investor's "foreign-currency exposure" bucket is *definitionally* 100% USD (there's no third currency for it to be split across). The risk score itself (0-100, "skew"/risk value near 100) reflects how much of the portfolio's value sits in that foreign-currency bucket — a real, high number if a large share of the portfolio's value is USD-denominated relative to a CAD home currency.
**Fix:** Extracted the gauge-mount logic into a shared `paintCurrencyRiskChart(P)` function and call it from **both** `paintPortfolioCharts()` and `paintRollupChart()`, so the gauge now renders correctly on both sub-tabs. Syntax-checked clean.

## 16. Currency Risk Exposure colour palette 🔧 REVISITED 2026-08-16 — fill-only fix wasn't enough
**Original fix (fill colors theme-aware) shipped, but you correctly reported it wasn't enough:** dark mode text inside the ring was still hard to read, and light mode just looked like "a brown circle" with no visible progress ring. Root cause of both: (a) ApexCharts' default **track** (the background ring the colored fill sits on) is a near-invisible light gray by default — against this app's own cream/navy cards, combined with the mid-band fill now correctly being the app's amber accent color, there was no visible ring boundary at all, just a filled disc; (b) the "XX/100"/"Risk score" text inside the ring never had an explicit color set, so it inherited an ApexCharts default not guaranteed to work against a dark card.
**Fix:** Added an explicit, purpose-built track color per theme (dark `#2b3244`, light `#e3d8c3`) — verified against all three possible fill colors (red/accent/green) in both themes, every combination clears 3.5:1+ (WCAG non-text minimum), so the ring is now always visually distinct from whatever's filling it. Text inside the ring now explicitly reads `--text-1` (the same token the rest of the app's primary text already uses) — 15-17:1 contrast against the card in both themes, verified. Also bumped the gauge size slightly (150→180px) and hollow/text sizing for better legibility. Syntax-checked clean.

**Second bug found from your follow-up ("Portfolio 0% CAD / 100% USD; skew 100%" never changes):** this wasn't a wording/display problem, it was **feeding the risk engine the wrong input**. Both call sites (`paintCurrencyRiskChart` and `portfolioGeoAndFxHtml`) pre-filtered the property list down to *only* foreign-currency properties before calling `ECON.currencyRiskExposure()` — so the engine's own `cadPercent`/`usdPercent` calculation was mathematically guaranteed to always compute 0%/100% and a maxed-out 100% skew, because by the time it saw the data, every CAD property had already been excluded. Confirmed by reading the engine's own source inside the bundle: `exposureConcentration`'s HHI-style concentration formula (`a²+n²` on the fractions) is *designed* to reward a diversified split and penalize a 100/0 one — it was never getting the chance to do that. **Fix:** both call sites now pass the whole portfolio (every property, each correctly tagged with its own real currency), so the engine computes the portfolio's genuine CAD/USD split and a real skew number — and the concentration-risk math now actually rewards your real diversification instead of always scoring worst-case. The "no foreign exposure" empty state was also updated to check for genuine foreign-currency holdings existing, rather than being tied to the old pre-filtered list. Syntax-checked clean.

Research pulled current (2026) WCAG 2.1-era dark/light mode guidance: avoid pure black/white surfaces, design each theme intentionally rather than inverting one into the other, keep body text ≥4.5:1 contrast, and the most common real-world failure is secondary/caption text that "looks fine" but was never actually contrast-checked. Sources: [inkbotdesign.com](https://inkbotdesign.com/dark-mode/), [onething.design](https://www.onething.design/post/best-practices-for-dark-mode-ui-design), [Cloudscape data-vis colors](https://cloudscape.design/foundation/visual-foundation/data-vis-colors/), [CleanChart dark-mode charts](https://www.cleanchart.app/blog/dark-mode-charts).

Then **measured** v2-remastered's actual tokens with a real WCAG relative-luminance contrast calculation (not eyeballed) — this is the important part: your complaint wasn't just "feels too bright," it was a genuine, measurable accessibility failure:

| Token | Old light-mode ratio (vs. white cards) | Verdict |
|---|---|---|
| `--text-3` (footnotes/chart-notes) | 3.03:1 | **FAIL** (needs 4.5:1) |
| `--accent` (gold) | 3.88:1 | **FAIL** |
| `--green` | 3.30:1 | **FAIL** |
| `--red` | 4.83:1 | pass |
| `--blue` | 4.10:1 | borderline fail |
| Dark mode `--text-3` | 3.44:1 | **FAIL** (dark mode you called "fine," but this one token was measurably under threshold too) |
