# InvestScape: Which Build Path Gets a Solo, Non-Technical Founder to a Paid MVP — And What to Avoid

## TL;DR
- **Build the financial engine as a standalone, well-tested JavaScript/TypeScript API from day one, and put a thin front end on top of it.** The portable core (IRR/XIRR, amortization, DSCR, capital stack) survives any front-end decision; the UI does not. This single architectural choice de-risks every other decision in this report.
- **For the front end, WeWeb + Supabase beats Bubble for this specific product** — because Bubble has no code export, meters you on unpredictable Workload Units, and forces the same hand-rebuild of the UI that WeWeb does, while WeWeb gives you Vue export, flat pricing, and cleaner separation. But do NOT attempt a fully vibe-coded Cloudflare/Claude Code build as your primary path: the security and operational evidence for non-technical owners running production financial apps is genuinely alarming.
- **Sequence: validate paid demand with a hosted calculator + waitlist first (~4–8 weeks, under ~CA$3–5k), then build the tiered SaaS on WeWeb+Supabase with a contractor for auth/billing/security (~3–5 months, ~CA$15–35k all-in).** Cut i18n, the Community module, and most data feeds from v1.

## Key Findings

1. **Bubble is a defensible choice but a poor fit for THIS product.** Bubble's 2026 pricing is Workload-Unit-metered and unpredictable; multiple sources report production SaaS bills of $1,500–$3,500/mo once plugins and WU overages are included, and there is **no code export** at all. For a calculation-heavy app the JS engine has to live outside Bubble's expression composer anyway, and the UI must be hand-rebuilt regardless of platform — so Bubble's main advantage (all-in-one simplicity) is partly neutralized while its worst attribute (lock-in) remains.

2. **WeWeb + Supabase (or Xano) is genuinely better on the axes that matter here, but is not a free lunch.** WeWeb exports a real Vue.js SPA you can host on Cloudflare/Vercel/Netlify, supports custom JavaScript in workflows and custom Vue components, and is Xano's officially-recommended front end. The caveats are real: WeWeb cannot import your hand-written HTML either (you rebuild the UI in its editor), exported code is "structured by a machine for a machine" and not cleanly hand-editable, and plugins that route through WeWeb microservices (Stripe, Auth, Airtable) break in self-hosted exports.

3. **The fully-coded "Claude Code + Cloudflare" path is now technically operable from a tablet, but is the highest-risk path for a non-technical owner handling financial data.** Claude Code runs on web and the Claude mobile app (Pro/Max), and Cloudflare's platform is cheap — per Cloudflare's official pricing docs, Workers Paid is "a minimum charge of $5 USD per month," with the Standard model including "10 million [requests] included per month +$0.30 per additional million" and "30 million CPU milliseconds included per month +$0.02 per additional million," and "no additional charges for data transfer (egress)." But the security evidence is damning: Veracode's 2025 GenAI Code Security Report (100+ LLMs, 80 tasks) found that "in 45% of the cases these models introduce a detectable OWASP Top 10 security vulnerability into the code," and Escape.tech's October 2025 production scan of 5,600 vibe-coded apps found 2,038 highly critical vulnerabilities, 400+ leaked secrets, and 175 instances of exposed PII "including bank account data." For an app touching Stripe, auth, and personal financial data under PIPEDA, this is an existential risk class for a solo owner who cannot audit the code.

4. **"Build it twice" is real and expensive, but the asymmetry in this product changes the calculus.** Migrating off Bubble is a full rebuild (no code export), realistically ~8–16 weeks and roughly $18k–$60k+ for a complex SaaS. But because InvestScape's core value is a portable calculation engine, you can make the expensive-to-rebuild part (UI) the cheap part and the valuable part (engine) permanent. Build the engine once, as an API, and the "second build" becomes just a new thin client.

5. **A merchant-of-record (Paddle or Lemon Squeezy) materially reduces burden for a Canadian founder selling internationally** — they become the seller of record and remit GST/HST/VAT/sales tax globally — at a cost premium of roughly 1.5–2 points over Stripe. For a solo founder this is usually worth it, though it means the checkout/billing UX is partly owned by the third party.

## Details

### Strand 1 — The 2026 no-code / low-code landscape

**Bubble (2026).** Confirmed via multiple 2026 sources (lowcode.agency, goodspeed.studio): Starter $29/mo (billed annually; $32 monthly) with 175K WU, Growth $119/mo ($134 monthly) with 250K WU, Team $349/mo with 500K WU, Enterprise custom; WU overages billed at $0.30 per 1,000 WU. Every DB query, workflow, and API call consumes WU; naive implementations compound the bill, and several practitioners report bill shock at small user counts. **No code export; vendor lock-in is total** — Bubble's own docs state apps "can only be run on the Bubble platform; there's no way of exporting your application as code." You can export **data** (CSV per data type, plus the Data API) but must rebuild all logic and UI to leave. ApexCharts is available via third-party plugins (multi-series supported). Native multi-language exists (per-user language field, URL param, CSV import/export of text strings) and is workable for four languages, though staggered/complex localization is manual. Stripe subscriptions work via Bubble's official plugin, but **downgrade/proration behavior is a known pain point** — the Bubble forums are full of founders struggling to schedule downgrades at period-end and to handle proration, because that logic really lives in Stripe and must be wired through the API Connector.

**WeWeb + Xano/Supabase.** WeWeb is a front-end builder (est. 2017) that pairs with an external backend. Strengths for this use case: exports a compiled Vue.js 3 SPA (hostable on Cloudflare/Vercel/Netlify), supports custom JavaScript actions and custom Vue components, no per-user fees, and is the front end Xano officially recommends. Xano and Supabase both give you real Postgres, row-level security, and SOC-2-grade backends (Xano advertises GDPR/SOC2/HIPAA/ISO 27001). Caveats: (a) you cannot import your existing HTML — the UI is rebuilt in WeWeb's editor, same as Bubble; (b) exported Vue code is machine-structured and not meant for hand-editing; (c) self-hosted exports break plugins that depend on WeWeb microservices; (d) the Bubble+Xano combo specifically suffers a **dual-auth conflict** (two user systems), which is why WeWeb+Xano or WeWeb+Supabase is the cleaner pairing.

**AI app builders (Lovable, Bolt.new, v0, Replit Agent, Base44).** These generate real React/Tailwind code you can own and export — a genuine advantage over Bubble. v0 excels at UI components (shadcn/Tailwind); Lovable/Bolt do fuller full-stack scaffolds with Supabase. They can accept pasted code/components as a starting point (Lovable, Bolt, Replit accept pasted React; v0 is coupled to shadcn). The market is large and real: per Founded.com/TechCrunch, Lovable hit $100M ARR (July 2025), $200M (Nov 2025), $300M (Jan 2026) and $400M ARR in February 2026, with TechCrunch (Mar 11, 2026) reporting it "added $100M in revenue last month alone, with just 146 employees," and CEO Anton Osika stating ~80% of revenue comes from founders building real applications. **But** the "technical cliff" is real: they produce something that looks finished but requires wiring auth, RLS, billing, and deployment — exactly where non-technical founders get stuck and where security failures concentrate. Base44's danger is documented: Wiz Research disclosed a platform-wide authentication bypass on July 9, 2025 (Wix patched within 24 hours) in which "by providing only a non-secret app_id value to undocumented registration and email verification endpoints, an attacker could have created a verified account for private applications," bypassing SSO.

**Plasmic.** Notable because its **code-component** model is the inverse of Bubble: you register your own React components (any npm library, your own CSS) and use them visually in Plasmic Studio, and Plasmic can generate code with a persistent design↔code connection. This is the most "bring your existing React/Claude-generated components" friendly of the visual builders. It requires a host React app, so it presumes some code infrastructure — better suited to a founder working with a contractor than fully solo-from-a-tablet.

**Webflow DevLink / Code Components.** DevLink now works both directions: **export** Webflow components → React (.tsx, high fidelity including interactions, but no ecommerce/CMS elements and no page-level custom code; class selectors get namespaced), and **import** React components → Webflow canvas ("Code Components," 2026, on CMS/Business plans; React Server Components not supported). Critically, **Webflow cannot ingest raw hand-written HTML/CSS/JS** — this is a long-standing wishlist item Webflow has explicitly declined to build ("Everyone codes their HTML/CSS differently so it would be very difficult to implement this"); the only workaround is the Embed element. So Webflow does not save you the UI rebuild either.

**FlutterFlow.** Full Flutter/Dart code export (paid), and supports custom Dart functions/actions/widgets plus pub.dev packages. But it's a Dart/Flutter platform — it cannot ingest your HTML/CSS/JS prototypes, and its Figma import is repeatedly reported as buggy/partial (an open, "status: confirmed" GitHub issue). Best when native mobile is the primary deliverable, which is not your case (you work on tablet but ship a web SaaS).

**Others.** Retool/Budibase/Appsmith are internal-tool oriented (great for admin panels, not customer-facing branded SaaS). Softr/Glide/Adalo are lighter and won't carry your calculation and charting complexity. Directus/Backendless are backend/headless plays. Noodl/Toddle are interesting visual+code hybrids but thin ecosystems for a non-technical solo founder.

**Verdict on Strand 1:** No visual platform will import your Claude-generated HTML with fidelity — every option requires rebuilding the UI. Given that constant, the tiebreakers become **lock-in, pricing predictability, and backend power**, and on all three WeWeb+Supabase beats Bubble. Plasmic is the best option *if* you accept a code-hosted host app.

### Strand 2 — The fully-coded path (Claude Code + Cloudflare)

**Cloudflare platform & cost.** Workers Paid is a $5/mo minimum (10M requests, 30M CPU-ms included, no egress charges — per Cloudflare docs above); D1 (serverless SQLite) bills only on rows read/written and storage with no egress fees; KV, R2, Durable Objects, Queues, Hyperdrive, Workers AI all usage-metered with generous free tiers. At 100 and 1,000 users a well-built SaaS plausibly runs in the ~$5–50/mo range; at 10,000 users likely low hundreds/mo — structurally cheaper than Bubble at the same scale (where WU overages and plugin fees push production apps into the $1,500–$3,500/mo band). The catch: those numbers assume competent engineering; the savings are real only if the app is built and operated correctly.

**Claude Code access in 2026.** Claude Code is available via terminal (CLI), desktop, **web (claude.ai/code)**, and the **Claude mobile app**, with a "Remote Control" bridge (research preview, Max tier) that lets you steer a local terminal session from a phone/tablet. Claude Cowork expanded to web and mobile (July 7, 2026). So the mechanical claim "operate it from a tablet" is now true. The problem is not access — it's judgment.

**The honest evidence on non-technical founders operating production AI-built SaaS.** It is *possible*: per Value Add VC (2026), "84% of AI coding tool users in 2026 have no engineering background," and "the $800K ARR virtual try-on tool is the most-cited example of a solo non-technical founder reaching real revenue." But the failure record is extensive and specific:
- **Veracode 2025 GenAI Code Security Report** (100+ LLMs, 80 tasks across Java/Python/C#/JavaScript): a detectable OWASP Top-10 vulnerability appeared in 45% of cases, with Java worst at a 72% failure rate, XSS failing 86% and log injection 88%; the March 2026 update ("Despite Claims, AI Models Are Still Failing Security") found the security pass rate flat at ~55% with no improvement from newer/bigger models — including slight declines for Claude Sonnet/Opus generations.
- **Escape.tech (Oct 2025)** scanned 5,600 publicly deployed vibe-coded apps (Lovable, Base44, Bolt.new, Vibe Studio) and found 2,038 highly critical vulnerabilities, 400+ leaked secrets, and 175 instances of exposed PII "including bank account data" — all live in production; a related 1,400-app subset showed 65% with security issues and 58% with ≥1 critical vulnerability.
- **Named incidents:** Moltbook (Jan 2026) shipped with its production DB fully exposed and no row-level security; the Base44 auth bypass (Wiz, July 2025) above; Lovable-built apps shipping credentials in client-side bundles; a Replit AI agent deleting a production database. Broken access control / BOLA (client-side-only enforcement of paid tiers and record ownership) is the single most common class — directly relevant to your Free/Pro/Enterprise gating.

**The maintenance/debugging burden.** When a production bug, failed migration, or billing error hits code you didn't write and don't understand, the only person who can debug it is you — and even you may not understand what the AI generated. There's typically no version control discipline, no audit trail of which prompt produced which feature, and no rollback plan unless you set one up. The debugging cycle for a security incident routinely exceeds the time "saved" by skipping tests.

**Non-obvious operational work you'd own:** database backups + tested restores, schema migrations, monitoring/alerting, error tracking, secrets management, incident response, uptime, and compliance. For a Canadian fintech-adjacent SaaS: **PIPEDA** (and Quebec Law 25) accountability + breach notification; **GDPR** if you take EU users; **PCI** considerations (mitigated by using Stripe/MoR hosted checkout so card data never touches your servers); and **SOC 2 Type II** expectations from enterprise buyers (a first Type II audit runs roughly CA$30k–$120k in Canada). A data breach of financial PII under PIPEDA is a notifiable event with legal exposure that can be existential for an early-stage solo company.

**Building blocks that reduce the burden.** Auth: Clerk, Auth0, Supabase Auth, Better Auth — do NOT hand-roll auth. Billing: Stripe Billing (most flexible), or a **merchant-of-record (Paddle ~5%+$0.50; Lemon Squeezy ~5%+$0.50)** which becomes the seller of record and remits GST/HST/VAT/sales tax globally. For a Vancouver founder selling into the US/EU/Asia, MoR removes an entire category of cross-border tax compliance for ~1.5–2 points over Stripe's effective rate. Note Lemon Squeezy has had reported edge cases with Canadian provincial tax that required manual correction, and Paddle has the deepest jurisdiction coverage.

**The viable hybrid.** A no-code/low-code front end calling a **separately deployed, properly engineered calculation API** is the strongest architecture in this whole analysis. It confines the hard, high-stakes code (math correctness, and — if the API also handles data — auth/RLS) to one well-tested, version-controlled service a contractor can build and you can keep, while the front end stays in a tool you can operate. This is also exactly how mature Bubble apps scale ("separate UI from heavy compute").

### Strand 3 — The "build it twice" question

**Is start-no-code-then-migrate validated or an anti-pattern?** Both, depending on architecture. Real companies (Meerako's Dallas client; multiple agency case studies) validated on Bubble, found PMF, then hit a "no-code ceiling" (performance, brittle workflows, custom-UI limits, lack of code ownership as an investor red flag) and migrated. Migration is a **full rebuild** — "you cannot simply export code from Bubble." Realistic 2026 figures for a complex SaaS cluster around **8–16 weeks and ~$18k–$60k+** (Goodspeed's tiered numbers: simple $8k–15k/4–6 wks; mid-complexity B2B SaaS $18k–35k/8–12 wks; complex/multi-tenant $35k–60k/14–20 wks), with AI tooling speeding UI scaffolding but NOT the hard parts (data modeling, workflow/auth/file migration, cutover). A candid practitioner (georgecollier, Bubble forum, May 2026) warns that "migrate your Bubble app in two weeks" claims "are mostly crap from people without apps running at any serious scale," that "the people advertising that they'll migrate your app based on your JSON file are basically vibe coding it," and that ~20% of Bubble workflows shouldn't be recreated at all.

**Counter-examples that stayed on Bubble.** Messly (25K doctors, acquired), Dividend Finance (billions in loans), Comet, LifeLegacy, Better Legal (~$1M ARR), Aware Health (~$30K MRR). The common thread: they either kept complexity modest OR used a **hybrid** (Bubble for UI/orchestration, external services for heavy compute). "High-throughput compute" and "inconsistent WU patterns" are cited as the top reasons teams leave — both of which describe a heavy financial engine.

**The threshold.** Products stay happy on no-code when compute is light, data volumes moderate, UI needs are standard, and the team values speed over ownership. They outgrow it when they need heavy/consistent computation, pixel-perfect custom UI, advanced integrations, sub-second performance, or code ownership for fundraising/exit. **InvestScape sits on the wrong side of most of these lines** — which is the core argument for not over-investing in a Bubble UI you'll throw away.

**The asymmetry, exploited.** Your JS financial engine is portable across every route; your UI is not portable across any of them. Therefore the correct architecture is to **build the engine once as a standalone, independently hosted, thoroughly unit-tested API** (Canadian semi-annual vs US monthly compounding, XIRR/MIRR root-finding, DSCR, GDS/TDS + stress test, CMHC premium, capital-stack, portfolio rollups), with a golden-test suite proving each formula against known-good outputs. Then any front end — WeWeb today, React tomorrow — is a thin client that POSTs inputs and renders the returned numbers (and hands them to Claude for the narrative layer). This makes the "second build" a UI-only project, not a from-scratch rebuild, and shrinks lock-in to near zero for the part that actually differentiates the product. (Note one migration nuance directly relevant to a calc-heavy app: Bubble apps often store denormalized "calculated values" on records; a coded rebuild should recompute those at query time rather than persist them — another reason to keep the math in an external engine from the start.)

### Strand 4 — Best path from mockups to MVP

**Clarifying the goal this strand optimizes for.** The intent is not "build the ideal architecture regardless of cost" — it's: bootstrap Route 1 as leanly as possible, get to paying customers (target: 1,000+), and use that revenue to fund a proper Route 2 team (IT/database, HR, finance) rather than needing outside capital. That reframes every recommendation below along one axis: **spend money only where skipping it would either block launch or create a liability you can't undo later** (security holes, billing correctness, data-loss risk). Everything else — full i18n, Community, SOC 2, Enterprise tier, a large contractor budget — is correctly deferred, and this was already the report's direction; this note makes the reasoning explicit rather than assumed.

This also sharpens *why* the portable-engine architecture matters: you're deliberately planning a full rebuild once revenue proves the model. If Route 2 is inevitable by design, the earlier logic gets stronger, not weaker — build the calculation engine once, properly, now, so that the "prove it, then rebuild" plan doesn't mean re-deriving Canadian semi-annual compounding, XIRR convergence, GDS/TDS stress tests, and capital-stack math a second time under a hired team. The engine is the one piece of Route 1 spend that isn't thrown away at the Route 2 rebuild — everything UI-side is.

Two things worth flagging against a fully self-funded, minimal-spend Route 1:
- **Security and billing correctness aren't optional even pre-revenue**, because the moment real customers enter real payment or financial data, a breach or billing bug is a liability that predates any hiring plan and can end the company before Route 2 is ever reached. The recommendation below is not "hire a full team," it's "spend on a narrow, fixed-scope review of exactly these two things," which is a materially smaller ask than the earlier phase-2 contractor budget implied.
- **1,000 paying customers is a real scale target, not a vague "some users."** At Bubble's WU-metered pricing or WeWeb+Supabase's usage-based backend costs, 1,000 paying customers running per-deal amortization/XIRR calculations is enough volume that platform cost becomes a real line item, not a rounding error — worth re-checking pricing tiers against that number specifically once you're closer to it, rather than assuming free/starter tiers hold.

**What to build first (least build to validate paid demand).** The core value is the engine, not the chrome. So:
1. **A single hosted deal-analyzer page** (one property, full Canadian mortgage + IRR/DSCR/equity-multiple output, one good chart) behind an email gate, plus a "Pro waitlist — reserve $29/mo founding price" button. This tests willingness to pay before the SaaS exists.
2. Instrument it: track how many analyses run and how many click the paid CTA. **Benchmark: pursue the full build only if you get meaningful paid pre-commitments or a strong analysis→CTA conversion from real target users (realtors/investors in your network).**

**What to cut/defer from v1:** the four-language i18n (ship English only; Canadian French second once revenue exists), the Community module (forum/reputation is a v2 growth feature, not a validation feature), most external data feeds (start with FRED + Bank of Canada Valet on a simple schedule; defer CMHC imports, Redfin CSVs, RSS), document data extraction, and the fancier portfolio-rollup analytics. Keep: the engine, single-property + basic multi-period projection, CSV import/export, Stripe/MoR billing with Free/Pro tiers (defer Enterprise), and the AI narrative layer.

**Recommended path, sequenced (solo, part-time):**
- **Phase 0 — Engine API (weeks 1–6).** Contract a strong full-stack/TypeScript developer to build the calculation engine as a standalone API on Cloudflare Workers (or a simple Node service), with a comprehensive test suite. This is the highest-leverage outsourcing dollar you will spend. ~CA$6k–15k.
- **Phase 1 — Validation front end (weeks 3–8, overlapping).** A single-page hosted calculator + waitlist calling the engine. Cheap; can be a v0/Lovable-generated static front end or a simple WeWeb page. ~CA$1k–3k.
- **Phase 2 — SaaS build on WeWeb + Supabase (months 2–5).** Rebuild the UI from your HTML mockups in WeWeb; Supabase for auth + Postgres + RLS (multi-tenant, downgrade-to-read-only via row flags, never delete); ApexCharts via WeWeb custom component; billing via Stripe or Paddle/Lemon Squeezy; Claude API for the narrative layer. Keep the engine as the external API. ~CA$8k–20k of contractor help for auth/RLS/billing/security review + your own build time.
- **Total realistic all-in to paid MVP: ~CA$15k–35k and ~4–6 months part-time**, versus a Bubble MVP at broadly similar build cost but with lock-in and WU-cost risk, versus a fully-coded build that is cheaper in platform fees but carries unacceptable security/ops risk for a non-technical solo owner.

**Where a contractor has highest leverage (outsource these):** (1) the calculation engine + tests; (2) auth, row-level security, and multi-tenancy setup; (3) Stripe/MoR billing including downgrade logic; (4) a one-time security review before launch. **Keep in-house:** the UI assembly in WeWeb, content, the AI prompt/narrative design, and day-to-day config — the parts you can safely operate from a tablet.

**Rates (2026):** Bubble specialists commonly $50–$150/hr (juniors $25–$50, top ~8% at $200+); freelance full-stack devs mid-level ~$50–$90/hr and senior React/Next specialists ~$100–$180+/hr; agencies run 20–40% above freelancer rates. Vet on: a portfolio of shipped, *operated* apps (not just launched); willingness to write tests; explicit workload/cost-efficiency mindset; and a clean handoff (repo access, docs). Scope fixed-price only where the spec is airtight (the engine) and hourly/retainer where it's iterative (the UI).

**De-risking checklist:** pre-sell founding subscriptions; keep the engine independently testable; never store card data (use hosted checkout/MoR); enable database backups + a tested restore before launch; run one paid security review; and don't build i18n/community until paying users ask.

## Recommendations

**Primary recommendation:** Adopt the **hybrid "portable engine + thin client" architecture**, ship the MVP on **WeWeb + Supabase**, use **Stripe or a merchant-of-record (Paddle/Lemon Squeezy)** for billing, and **hire a vetted contractor for the engine, auth/RLS, billing, and a pre-launch security review.** Do not build the whole product on Bubble, and do not vibe-code the whole product yourself on Cloudflare.

**The strongest argument against my own recommendation:** WeWeb+Supabase still forces you to hand-rebuild the entire UI (same as Bubble), still leaves you dependent on a contractor for the risky pieces, and adds the coordination overhead of a two-vendor (front end + backend) stack that a pure Bubble build would avoid — so if your true constraint is "I must ship something entirely by myself, this month, from a tablet, with zero contractor budget," then a Bubble MVP (accepting the lock-in and rebuilding later) is the more honest choice, and the report's engine-first architecture is what makes even that Bubble path survivable. My recommendation is right *because* you can afford a modest contractor budget and the product's value is the math; remove either of those and it weakens.

**Staged next steps:**
1. **Now → week 6:** Contract the calculation engine as a standalone, tested API. Simultaneously stand up a one-page hosted calculator + paid waitlist.
2. **Week 6 checkpoint (go/no-go):** If you have real paid pre-commitments or strong analysis→CTA conversion from target users, proceed. If not, iterate the offer before building the SaaS.
3. **Months 2–5:** Build the multi-tenant SaaS on WeWeb+Supabase (English only, Free/Pro tiers, engine as external API, Claude narrative layer, ApexCharts). Contractor handles auth/RLS/billing/security review.
4. **Post-launch:** Add Canadian French, then Chinese; add data feeds (FRED/BoC first); add the Community module; consider Enterprise tier and a SOC 2 Type II track only when enterprise demand is concrete.

**Thresholds that would change the recommendation:**
- If validation shows demand for a **mobile-native** app → reconsider FlutterFlow (code export, Dart) for the client.
- If you land a **technical co-founder or a durable senior contractor relationship** → skip WeWeb and go straight to a coded Next.js/Supabase (or Cloudflare) client on top of the same engine, capturing the cost/perf/ownership upside safely.
- If WeWeb's per-project constraints or Vue export limits bite → the engine's portability means you swap only the front end, not the whole system.
- If enterprise buyers demand **SOC 2 / data residency** early → prioritize Supabase's Canadian region + the compliance track sooner.

## Caveats
- **No-code comparison content is heavily affiliate-driven.** Much of the pricing/scalability commentary (WeWeb's own comparison pages, Adalo's Bubble-pricing post, agency migration blogs like Goodspeed/Meerako/DBB) is commercially motivated; I've treated vendor and agency claims as unverified and flagged them. Bubble's official pricing tiers and "no code export" statement, Cloudflare's and Stripe's docs, and the WeWeb/Plasmic/Webflow/FlutterFlow official docs are the most reliable inputs.
- **Migration cost/timeline figures ($18k–$60k, 8–16 weeks) come largely from agencies that sell migrations** and should be read directionally, not as quotes. The strongest independent counterweight is the georgecollier Bubble-forum practitioner post, which pegs realistic complex migrations at ~3 months and debunks the fast/cheap claims.
- **Security statistics** (Veracode 45%, Escape.tech's 5,600-app scan, the 91.5% Kingbird figure) come from security firms with a commercial interest in the problem; however, the direction is corroborated across at least five independent studies (Veracode, Escape.tech, Apiiro, GitGuardian, Kingbird), which makes the overall finding hard to dismiss even if any single number is contestable.
- **Bubble's exact 2026 WU allocations and plan prices vary between sources** (e.g., Starter cited at both $29 annual and $32 monthly; WU counts differ slightly); confirm on bubble.io/pricing before budgeting.
- **Claude Code "Remote Control" and Cowork mobile** were research previews/rolling betas as of mid-2026; tablet-first operation may still have rough edges. Verify current availability on your plan.
- **The Cloudflare-vs-Bubble cost comparison at 100/1,000/10,000 users is an informed estimate assembled from separate pricing sources**, not a single benchmarked figure; treat the specific dollar bands as directional.
